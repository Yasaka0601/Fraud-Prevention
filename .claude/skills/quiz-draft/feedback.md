# ユーザーからのフィードバック記録

クイズ作成中にユーザーからもらった指摘をためておくファイル。
スキル実行時は「1. 準備」で全部読み、ここに書かれたことを守る。
追記は「8. 振り返り」でユーザーの確認をもらってから行う。

## 2026-10-25（テーマ：メール）

### 問題文・選択肢
- 「よく聞く」など、人によって感じ方が違う主観的な表現を使わない
- 用語の説明が長くなる問題は、用語を問う問題を別に作って分ける（例：「DMARCとは？」を分けた）
- 「（複数回答可能です）」は問題文に書かない（正解が複数なら画面に「※複数選択可」が自動で出る）。以前は「正解が2つ以上の問題だけに書く」と記録していたが、2026-11-11 にユーザーが訂正

### 解説
- 出典を開かなくても理解できるように書く（出典ありきにしない）
- 【ほかの選択肢が違う理由】の箇条書きは分かりやすいと好評
- 出典の中の大事な一文（背景・理由）は、解説に取り込む（例：個人情報流出が相次いだ時期と、氏名入りメールの関係）
- 数字は「誰の調査の、何のうち何%か」を書く

### 進め方
- 修正版を出すときは、解説だけでなく問題文・選択肢も含めた全文を出す（上にスクロールして確認させない）
- 検証エージェント（Opus）は知識が多く、作り直しても正解されることがある。2〜3回作り直しても正解される場合は、検証結果を添えてユーザーに判断をあおぐ
- ユーザーの質問には、まず質問に答えてから修正案を出す

## 2026-11-13（テーマ：最近増えている手口）

### 問題文・選択肢
- 統計の数字を問うクイズは作らない。翌年には古くなって使えなくなる。手口の流れや仕組みを問う
- 選択肢どうしの数字や割合がほぼ並んでいるものは、正解と不正解の差がはっきりしないので使わない

### 解説
- 問題文に書いていない事実（例：「DMは偽アカウントから届いていた」）を、解説で後から言い切らない。必要なら問題文に手がかりを入れて（例：「同じ名前・同じアイコンのアカウントから」）、問題文と解説を合わせる
- 「エサ」のような、くだけた比喩や品のない言い方を使わない。「信用させるため」のように、そのまま書く
- 短くするときも、場面の流れ（何をさせられて → 何を言われるか）を省かない。いきなり結論から書くと唐突になる

## 2026-11-13（テーマ：最新のセキュリティ対策）

### 解説
- 問題文の場面に偽サイトや偽SMSが出てくるときは、解説の最初の文で「このログイン画面は犯人が作った偽サイトです」のように、偽物であることをはっきり書く
- 裏で起きている流れ（犯人が何をして、何が届くか）は、①②③…と番号を付けて順に書くと分かりやすい

### 進め方
- 問題を解かせる検証エージェントは、Opusだと知識が多すぎて全問正解されやすい（2回作り直しても全問正解された）。SKILL.md で Haiku に変更済み。解説チェックは Opus のまま

## 2026-11-13（テーマ：ニセ警察官）

### 問題文・選択肢
- 問題文の最初の文で、場面のきっかけを書く。「〇〇しようと考えています」のように理由なしで行動を始めると唐突に読める（例：「知らない番号からの電話が増えたので、〜を入れることにしました」）
- 括弧での補足は増やしすぎない。用語は分かりやすい方を1つだけ使う（例：「検事（検察官）」ではなく「検察官」）。説明が必要な言葉は、括弧ではなく文の中で言い換える
- 家族で解くアプリなので、性的な要求を含む手口は扱わない

### 解説
- 出典は1問につき2つまでにする
